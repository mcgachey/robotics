# Phase 0: Building the Pi Server

Status: draft. Companion to `plan.md`. Describes how a bare Raspberry Pi OS install becomes the Phase 0 server, and what must be installed on the Pi. It applies the **config time / classroom time** split and the stack from `../../architecture.md` ("Pi lifecycle", "Implementation stack and delivery").

## 1. Model

| | **Config time** (internet available) | **Classroom time** (no internet) |
|---|---|---|
| Pi network | Uplink to a normal network | Offline classroom router only |
| Activities | `git pull`, install build tools, **build on the Pi**, deploy, self-check | Run the server. Nothing else |
| Internet use | Yes: GitHub, apt, PyPI, npm, Maven Central | **None.** No downloads, no `apt`, no update checks |

- **The GitHub repo is the only source.** The Pi gets code with `git clone` and `git pull`.
- **The Pi builds its own infrastructure.** There is no prebuilt bundle. Build tools are installed on the Pi, and Makefiles compile and deploy everything on it.
- **Two scripts in `bin/`, each with an optional branch argument (default `main`).** `bin/init_rp.sh` takes a bare Raspberry Pi OS install to a working server, and holds all one-time configuration. It is idempotent. `bin/update_rp.sh` is the routine update, and assumes `init_rp.sh` already ran **with the same branch**.
- **Makefiles own the pipelines**: *compile* (`make build`) and *deploy* (`make deploy`). The scripts call the same targets a developer runs by hand.
- The build tools stay installed on the Pi. At classroom time they work as long as nothing needs the internet (for example, a rebuild from already-fetched dependencies). Anything that downloads waits for config time. Nothing in the running system makes an outbound request.
- **The Pi is cattle.** It runs the code on one specific branch and can be wiped and rebuilt from scratch at any time with `init_rp.sh`. There is no in-place repair, versioning, or rollback. `data/` (student work) is never touched by build or deploy, so back it up if it matters before reimaging.

## 2. Dependencies on the Pi

All are installed at config time. Items marked **build** are needed only to compile and deploy. Items marked **run** are needed at classroom time.

### 2.1 Operating system

| Item | Requirement | Notes |
|------|-------------|-------|
| OS | Raspberry Pi OS Lite, 64-bit (Debian 12 "Bookworm" or later) | No desktop. Starting point: a bare install with SSH and network configured. |
| Architecture | `aarch64` | Match the Node and JDK downloads. |
| Storage | SSD over USB preferred, otherwise a good SD card | The Node build and `node_modules` need a few hundred MB during config. Student data is small. |
| Swap | At least 1 GB (config time) | `vite build` can exceed RAM on a 2 GB Pi. |
| Users | A dedicated `robotics` user runs the service (**run**) | Both scripts run as an admin user with `sudo`. |
| Directories | `/opt/robotics` (venv and app), `/var/lib/robotics/data` (data), `/etc/robotics` (config and secrets) | Data is on one filesystem so temp-then-rename writes are atomic (plan section 4.2). |

### 2.2 System packages (apt)

| Package | Why | Build / Run |
|---------|-----|-------------|
| `git` | Clone and pull the repo | build |
| `make` | Pipelines | build |
| `build-essential` | Compile any Python wheel that has no arm64 build | build |
| `curl`, `ca-certificates`, `unzip`, `xz-utils` | Downloads (Node, JUnit jars) and unpacking | build |
| `python3`, `python3-venv`, `python3-pip` | Server runtime and its virtualenv. Bookworm provides 3.11 | build and run |
| `openjdk-21-jdk-headless` | `javac` for student code and `java` for tests. See 2.4 | build and run |
| `procps` | `ps` and `pkill`, for checking orphan processes | run |
| `jq` | Self-check and acceptance scripts | build and run |

Nothing is installed from `apt` at classroom time. `unattended-upgrades` and the `apt-daily` timers are disabled at the end of config (section 6).

### 2.3 Python (server) (D1, D5)

A **single virtualenv** at `/opt/robotics/venv`, created by `make build` (if missing) and updated with `pip install -r server/requirements.txt` (pinned versions, with hashes, from PyPI at config time).

| Package | Use |
|---------|-----|
| `flask` | The web and API application. Brings `werkzeug` (password hashing and signed sessions), `jinja2`, `click` (CLI commands) |
| `gunicorn` | Production WSGI server: one worker, several threads |
| `pytest` | Server tests (`make test`), build only |

Everything else uses the standard library: `subprocess`, `os.killpg`, `threading`, `json`, `pathlib`, `hashlib`. Add a package only with a reason. A config file for the session secret key lives in `/etc/robotics`, is generated by setup, and is kept out of git.

### 2.4 Java (student code toolchain) (D2, D6)

| Item | Requirement | Why |
|------|-------------|-----|
| JDK | **OpenJDK 21 (arm64)**, from `apt` | The build service starts `javac` and `java` as child processes. Needs a JDK, not a JRE. |
| Target level | `javac --release 8` | `--release` exists only on JDK 9 and later, so a Java 8 JDK cannot run the plan's compile command. JDK 21 supports it (Debian 13 "trixie" has no JDK 17). |
| JUnit | `junit-4.13.2.jar`, `hamcrest-core-1.3.jar` | Downloaded by `make deps` from Maven Central, verified against `deps/checksums.txt`, and copied into the app. |
| `robotics-api.jar` | Built by `api/Makefile` with `javac --release 8` | `Program`, `Robot`, `MockRobot`, `ProgramRunner` (plan section 3). |

Caveat: student code is compiled for Java 8 but run on JDK 21. If this matters, also unpack a Temurin 8 arm64 JDK (not on `PATH`) at config time and run the Java tests against it once.

### 2.5 Node (UI build, **build only**)

| Item | Requirement | Notes |
|------|-------------|-------|
| Node.js | A pinned LTS (22.x) arm64 tarball from nodejs.org, unpacked to `/opt/node`, with the version and checksum in `deps/` | Bookworm's own `nodejs` package is too old for current Vite and Mantine, so use the pinned tarball. Setup puts it on `PATH` for `make` only. |
| npm packages | Installed with `npm ci` from the committed `package-lock.json` | `react`, `react-dom`, `@mantine/core`, `@mantine/hooks`, `@mantine/notifications`, `@monaco-editor/react`, `monaco-editor`, `vite`, `typescript`, plus a test runner (`vitest`). |
| Output | Static files in `web/*/dist`, copied into the app | Node is **not needed at classroom time**. Flask serves the built files. |

Monaco is bundled from the `monaco-editor` package, and the editor wrapper is configured to use that local copy so it never loads from a CDN. The pages must make no request to another host. `make check` greps the built output for external URLs, and the self-check confirms it in a browser (section 5).

## 3. Installed layout on the Pi

```text
/opt/robotics/
  venv/                          # the one Python environment
  app/                           # installed by make deploy (replaced each deploy)
    server/                      # Flask application
    web/ide/  web/instructor/       # built React apps (dist)
    lib/  robotics-api.jar  junit-4.13.2.jar  hamcrest-core-1.3.jar
    lessons/  scripts/
/opt/node/                       # Node (build only)
/etc/robotics/                   # server.env (port, limits, SECRET_KEY), mode 600
/var/lib/robotics/data/          # students, lesson enabled state, workspaces, builds, queue
/srv/robotics-src/               # git checkout of the deploy branch; the Pi builds from it (node_modules and caches live here)
/etc/systemd/system/robotics.service   # gunicorn from /opt/robotics/app, using /opt/robotics/venv
```

## 4. Procedures

### 4.1 First install: `bin/init_rp.sh [branch]`

On a bare Raspberry Pi OS install with internet connected:

```bash
sudo apt update && sudo apt install -y git
git clone --branch main https://github.com/<owner>/<repo>.git /srv/robotics-src
cd /srv/robotics-src && sudo bin/init_rp.sh          # or: sudo bin/init_rp.sh <branch>
```

The branch argument is optional and defaults to `main`. The scripts find the repo from their own location, so the checkout can be anywhere, but it must already be on that branch. `init_rp.sh` is idempotent (safe to run again), uses `set -euo pipefail`, and logs to a file. It does, in order:

1. Check that it is running as root on 64-bit Raspberry Pi OS, that the internet is reachable, and that the checkout is on the requested branch. Stop with a clear message otherwise.
2. `apt update` and install the packages in 2.2. Create swap if it is too small.
3. Download and verify the pinned Node tarball into `/opt/node`.
4. Create the `robotics` user and the directories in section 3. Generate `/etc/robotics/server.env` with a random secret key if it does not exist.
5. Create the venv at `/opt/robotics/venv` if it is missing.
6. Install and enable the `systemd` unit. Disable `apt-daily` timers, `unattended-upgrades`, and boot waits for the network (section 6).
7. Record the repo path and branch in `/etc/robotics/init.env`. This is how `update_rp.sh` knows init has run, and for which branch.
8. Run `bin/update_rp.sh <branch>` for the first build and deploy.
9. First install only (skipped if the instructor account already exists): `make bootstrap-instructor USER=...` (prompts for a password). Lessons come from the repo and deploy with the app. The instructor enables them in the instructor app.
10. Print instructions for the offline check (section 5).

### 4.2 Update: `bin/update_rp.sh [branch]`

```bash
cd /srv/robotics-src && sudo bin/update_rp.sh        # or: sudo bin/update_rp.sh <branch>
```

Same optional branch argument (default `main`). It assumes `init_rp.sh` has already run. It does not install packages or change system configuration. It:

1. Check that `/etc/robotics/init.env` exists and was written for the same branch. If not, stop with a message to run `init_rp.sh` with that branch (or re-image).
2. `git fetch`, then `git reset --hard origin/<branch>`. The Pi is cattle, so local changes in the checkout are discarded.
3. `make deps build test deploy check`: fetch pinned dependencies, build, test, install into `/opt/robotics/app`, restart the service, and run the self-check.

If it fails, fix the cause in the repo and run it again. If the Pi ends up in a bad state, don't repair it: re-image it and run `init_rp.sh` again (see section 1). To switch a Pi to another branch, treat it the same way and re-run `init_rp.sh <new-branch>`.

### 4.3 Classroom time

1. Connect the Pi to the classroom router only (no uplink).
2. `systemd` starts the server at boot. Students and instructor use the web apps. Nothing is built or installed.

Anything that needs a download, a rebuild, or an update waits for config time.

## 5. Offline self-check (end of config time)

`make check` runs `scripts/self-check`. Run it once more with the uplink **disconnected**, ideally after a reboot:

- `java -version`, `javac --release 8 -version`, and `python3 --version` work.
- The service is up, and the acceptance test (plan section 7) passes through the HTTP API, with `curl --max-time` so a hidden network call shows up as a timeout.
- Loading the IDE in a browser works, with the network panel showing **only requests to the Pi**.
- A deliberate infinite loop and a deliberate output flood are killed, and `ps` shows no orphan JVMs. Stop and timeout kill the whole process tree.
- Cold compile plus test time for Lesson 0 is recorded. This sets the build-latency target (architecture section 1).
- Server restart and a power cycle leave `data/` intact (plan section 7, step 10).
- Memory with a few concurrent jobs stays within the Pi's RAM (check which Pi 4 model: 2, 4, or 8 GB).

## 6. Keeping the Pi quiet at classroom time

Background services can make network calls with no help from our code. At the end of config time, turn off:

- `apt-daily*` timers and `unattended-upgrades`.
- `motd` and `apt-news` update messages.
- Boot waits for the network (`systemd-networkd-wait-online`), so the Pi boots quickly offline.

The Pi has no NTP at classroom time, so its clock may drift. Decide between setting it at config time, adding an RTC module, or accepting drift (open item).

## 7. Open items

- **Pi 4 RAM size**: it sets the thread and concurrency limits, each child JVM's `-Xmx`, and whether the Node build needs swap.
- **Python dependency policy**: pip with `--require-hashes`, or a lock tool such as `pip-tools`.
- **Node version**: confirm the LTS (22.x) works with the pinned Vite and Mantine versions on arm64.
- **Real Java 8 check** (section 2.4).
- **Config-time uplink**: Ethernet, or temporary WiFi (architecture TODO under "Pi lifecycle").
- **Clock at classroom time**: manual set, RTC, or drift (section 6).
- **Repo location and access**: public GitHub repo, or a deploy key for a private one.
